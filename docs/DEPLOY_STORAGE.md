# 部署磁盘管理

生产部署在上传前执行 `deploy/storage.py prepare`：检查 `/opt/todesk` 和 Docker 数据目录的可用空间。任一目录所在文件系统不足 8 GiB 时，先清理过期项目镜像，再检查；仍不足则停止上传，提示人工检查占用或扩容。8 GiB 是初始固定门槛，不是任意大小镜像的空间保证，镜像增长后需要重新评估。

## 镜像保留

- `/opt/todesk/.successful-images.json` 记录最近三次不同的成功部署（当前版本及两个回滚版本）。只有证书同步服务和 API 健康检查通过后才更新记录并清理。
- 清理仅限工作流配置的 backend、web、caddy、cert-sync 四个仓库的 40 位提交 SHA 标签；不使用全局 prune、不删除容器或数据卷。
- 所有现有容器（包括停止的容器）引用的镜像 ID 额外受保护。因此保留数量可能超过三个版本。
- 首次采用规则时，从现有容器初始化保护记录。无法可靠恢复过去的成功部署记录，其他历史 SHA 标签可被清理；之后逐步积累两个回滚版本。
- 保留镜像不等于完整回滚方案：数据库迁移、配置文件需结合已有数据库备份与对应 Git 提交处理。

## 上传文件

每次运行使用 `/opt/todesk/.deploy/<run_id>-<run_attempt>/`，SCP 外层临时压缩包也写入该目录。导入成功后才复制本次配置文件到部署目录。

远程部署脚本的 EXIT trap 和 Actions 的 `always()` 清理步骤均只清理本次目录。服务器断电、SSH 不可达或工作流被强制终止时无法保证清理完成；这类遗留会被空间检查发现，需要人工确认对应运行已结束后处理。旧流程留在其他位置的压缩包不会自动删除。

## 告警

每小时运行磁盘检查，不构建、不部署。任一被检查文件系统达到 80% 使用率时输出 warning 并让检查任务失败，使用 GitHub Actions 自带失败通知；请在 GitHub 通知设置中订阅该仓库的 Actions 失败通知。定时任务由 GitHub 调度，可能有延迟，不能替代需要实时告警的主机监控。

服务器需要 Python 3、Docker CLI 和 base64。脚本通过 SSH 环境传递并在内存中执行，避免磁盘已满时连检查脚本都无法上传。生产部署串行执行；只读监控使用独立并发组，避免定时任务挤掉排队的部署。
